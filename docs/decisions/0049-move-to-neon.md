# 0049. Move the database and sign-in from Supabase to Neon

**Status:** Accepted · 2026-11-19 · Changes how 0007, 0025, 0026 and 0043 are carried out (their rules stay)

## Context

Supabase's free plan allows two projects, and the owner needs the slot. Neon's free plan allows many projects, and is Postgres too, so the data model, row-level security and database functions can move as they are. Two things can't: Supabase's sign-in service, and the triggers on Supabase's `auth.users` table that enforced the sign-up rules (at most 25 accounts, Google only, invite required) and gave each new account a household.

## Decision

- **Database: Neon Postgres.** The same migrations, now in `db/migrations/`, with `auth.users` → `neon_auth."user"` and the role `anon` → `anonymous`. Applied by a small script (`npm run db:status`, `npm run db:migrate`) that records what ran in `migrations.applied`; each file runs in one transaction.
- **Queries: Neon's Data API**, which speaks the same protocol (PostgREST) as Supabase's. The 83 `.from()` / `.rpc()` calls in `features/` are unchanged; only `lib/server/db.ts`, which builds the client, is new. Each request sends the signed-in person's short-lived token, so row-level security still decides what they see. This is the adapter pattern: the provider changed behind one file.
- **Sign-in: Neon Auth** (Neon's hosted Better Auth), still Google plus the one demo password account, still server-side only with HttpOnly cookies (0007). Signed-out pages use Neon's anonymous token, which maps to the `anonymous` database role.
- **Sign-up rules: a signed webhook instead of a trigger.** Neon doesn't allow triggers on its sign-in tables. Before it creates any account, Neon Auth calls `app/webhooks/neon-auth` (`user.before_create`) and waits; the route checks Neon's signature (Ed25519, with a timestamp against replays), then asks the database function `private.check_signup(email, provider)`, which holds the same three rules as before. If the route is down, slow or errors, Neon refuses the sign-up (fail closed).
- **After sign-up:** `private.finish_signup(user_id)` gives the account its household and uses up its invite code. It is called by the `user.created` webhook and again by the sign-in callback, and is safe to repeat (idempotent), so it doesn't matter which arrives first.
- **Least privilege for the webhook:** it has no signed-in user, so it connects with its own database login, `signup_gate`, which can run those two functions and nothing else (a test and a check against the live database both confirm it can't read a single table). Its password is generated by `npm run db:gate-password` and lives only in the server environment.

## Alternatives considered

- **Run Better Auth inside the app** with its tables in our own schema, keeping real triggers. The rules would stay purely in the database, but the app would own session handling, auth secrets and a key endpoint: more code to get wrong for a two-person app.
- **Drop the Data API and write SQL from the server.** Closer to a typical Neon app, but it rewrites every query and loses automatic row-level security; about three times the work.
- **Keep Supabase and move a different project.** This project is the one most tied to Supabase; it was still the one the owner chose to move.

## Consequences

- The sign-up rules are still one SQL function, tested against real Postgres, but they are now _asked_ by the app rather than _fired_ by the database. A sign-up needs the app to be up; if it isn't, nobody new gets in, which is the safe direction.
- The 25-account check is no longer inside the same transaction as the insert. It can't be raced past the limit in practice: every account except the admin and the demo needs an invite, and invites plus accounts are capped at 25 when the admin approves them.
- Existing accounts get new ids on Neon (Google users simply sign in again; the demo account is recreated), so the data move maps old ids to new ones by email.
- One more network hop per request (fetching the person's token from Neon Auth). Measure it on the deployed site.
- Neon's free database sleeps after five minutes idle and takes a moment to wake; Supabase's paused after a week and had to be woken by hand.
- New server settings: `NEON_AUTH_BASE_URL`, `NEON_DATA_API_URL`, `NEON_AUTH_COOKIE_SECRET`, `SIGNUP_GATE_DATABASE_URL`. Nothing is `NEXT_PUBLIC_` any more.
